# 技術堆疊決策

為個人創業者或小團隊準備的一套精簡、有主見的預設技術堆疊，以及什麼時候才真的值得再加東西。

> **執行結論。** 目前的技術堆疊已經很強。更好的最佳化方向是整併：保留能持續提升開發速度的系統，移除功能重疊的服務，並把 Redis、專用向量搜尋、深度可觀測性與專用回饋工具視為選配層，而不是預設。

## 1. 建議的核心技術堆疊

在引入更多基礎設施之前，這是值得拿來上線並擴展一個正式 SaaS 的預設堆疊。

| 層級 | 預設 | 為什麼值得保留 |
| ----- | ----- | ----- |
| 開發 | **Claude / Codex** | 程式碼生成、審查、除錯，加速實作。 |
| 版本控制 | **GitHub** | 程式碼、pull request、issue 與 CI/CD 整合的單一事實來源。 |
| 應用程式／部署 | **Vercel** | Next.js／TypeScript 產品的最佳預設；維運負擔低。 |
| 後端／資料庫 | **Supabase** | Postgres、儲存、身分驗證、即時功能、佇列／排程（cron）與向量支援，集中在同一個平台。 |
| 金流 | **Stripe** | 計費、訂閱、Checkout、webhook 與客戶入口網站。 |
| 電子郵件 | **Resend** | 交易型郵件，開發者體驗簡單。 |
| DNS／邊緣 | **Cloudflare** | DNS、CDN／安全控制、邊緣服務，也可兼作網域註冊商。 |
| 產品分析 | **PostHog** | 數據分析、工作階段重播、功能旗標、實驗——對許多早期產品來說，可觀測性已經足夠。 |

## 2. 應從預設堆疊移除的項目

**Pinecone → Supabase pgvector。** 對於一般具備 RAG、語意搜尋或 embedding 的 SaaS，把向量放在 Postgres 裡比較簡單。這樣可以避免雙重寫入、中繼資料同步、刪除同步，以及多一個網路相依。只有在檢索是核心工作負載、而且 pgvector 已被證實是瓶頸時，才引入 Pinecone。

**Clerk → Supabase Auth**，除非 B2B 身分管理本身就是產品功能。Supabase Auth 足以處理標準使用者帳號、社群登入、magic link，以及與資料庫結合的授權。當完善的組織管理、邀請、角色權限控管與租戶切換能實質改善 B2B 產品時，Clerk 才值得加入。

**Sentry → 與 PostHog 並用時為選配。** PostHog 現在涵蓋的數據分析、重播與錯誤可視性，已足以成為可信的早期預設。當團隊需要更深入的例外分析、追蹤（tracing）與正式環境除錯時，再加入 Sentry。到那時分工就有意義：PostHog 解釋使用者行為；Sentry 解釋應用程式故障。

**Namecheap → 選配。** 由於 Cloudflare 已經負責 DNS，把註冊商一併整合比較方便。把註冊商分開也說得通，可以作為帳號隔離與安全上的選擇——這是維運偏好，不是技術要求。

## 3. 應依需求才加入的服務

| 服務 | 什麼時候加入 | 預設立場 |
| ----- | ----- | ----- |
| **Upstash / Redis** | 快取、速率限制、暫態狀態，或確實能受益於 Redis 的工作負載。 | 不要因為「每個 SaaS 都需要 Redis」就加入。 |
| **Pinecone** | 專用、高流量的檢索，或進階向量搜尋需求。 | 量測到 pgvector 的限制之後再加入。 |
| **Sentry** | 正式環境的除錯需求超出 PostHog 的能力。 | 當問題診斷開始耗費可觀的工程時間時再加入。 |
| **ProductBridge** | 回饋量大到整併、去重與排定優先順序都變得痛苦。 | 早期用 PostHog 問卷＋客服＋簡單的待辦清單就夠了。 |
| **Cloudflare R2** | 大型公開檔案、大量媒體頻寬，或物件儲存的成本結構值得時。 | 先用 Supabase Storage。 |
| **Clerk** | 組織、團隊邀請、複雜的 B2B 角色權限控管，或身分驗證體驗具有策略重要性時。 | 否則使用 Supabase Auth。 |

## 4. 架構原則

* 只保留一個記錄系統（system of record）。凡是可行，持久性的應用資料都應由 Postgres 持有。
* 在通用資料庫未能滿足某個經過量測的需求之前，不要引入專用資料庫。
* 讓同步請求路徑保持精簡。把郵件、embedding、檔案處理、報表與長時間執行的 AI 工作移到佇列或工作流程。
* 依據負載、可靠性或產品需求增加基礎設施——而不是依據預期中的規模。
* 為可逆性最佳化。以 Postgres 為中心、樸素、可攜的架構，通常比優雅的專有抽象層更可取。
* 每個供應商都有持有成本：SDK、機密、webhook、帳單、服務中斷、權限、監控與資料同步。

## 5. 背景工作：唯一需要刻意規劃的能力

非同步執行比多一個資料庫更重要。典型工作負載包括 Stripe webhook 處理、電子郵件、embedding 生成、檔案轉換、排程清理、外部同步，以及長時間執行的 AI 任務。

| 需求 | 優先使用 |
| ----- | ----- |
| 簡單的排程任務 | **Vercel Cron** |
| 由資料庫驅動的非同步工作 | **Supabase Queues / Cron** |
| 長時間執行的應用程式或 AI 工作流程 | **Vercel Workflows** |
| 快取／速率限制／暫態狀態 | **Upstash Redis** |

## 6. 最終技術堆疊

**核心——用這些上線**

* Claude / Codex
* GitHub
* Vercel
* Supabase
* Stripe
* Resend
* Cloudflare
* PostHog

**選配——只在觸發條件真的出現時才加入**

* Clerk——B2B 身分管理
* Sentry——深度可觀測性
* Upstash——Redis 工作負載
* Pinecone——向量規模
* ProductBridge——回饋量
* R2——物件儲存成本

> **營運原則。** 從能安全上線產品的最小技術堆疊開始。只有當某個供應商能消除一個經過量測的限制，或創造的產品優勢大於它持續的維運成本時，才加入它。
