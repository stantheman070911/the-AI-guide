# 神聖三位一體 + 1

一套可重複使用、適用於 AI 輔助程式開發專案的文件系統：三份文件分別回答「做什麼」、「怎麼做」與「現在怎樣」——也就是「神聖三位一體」——再加上治理它們的憲章。第五份選配文件（維運手冊，runbook）在專案有了真正的部署之後，負責承載維運程序。

把這個資料夾裡的範本複製到新專案的 `docs/` 資料夾，填入佔位內容，再刪掉不適用的部分。

## 五份文件

| 文件 | 回答的問題 | 權威性 |
| --- | --- | --- |
| [`CONSTITUTION.md`](CONSTITUTION.md) | 這個專案必須怎麼打造？ | 永久規則 |
| [`BRIEF.md`](BRIEF.md) | 我們要做什麼、為什麼？ | 產品事實 |
| [`PLAN.md`](PLAN.md) | 我們打算怎麼做？ | 執行事實 |
| [`LOG.md`](LOG.md) | 現在實際上發生什麼事？ | 營運記憶 |
| [`RUNBOOK.md`](RUNBOOK.md) | 我們怎麼發布、啟用與復原？ | 維運程序 |
| 程式碼 + 測試 + Git | 實際上存在什麼？ | **機器事實** |

最後一列是其他一切都要服從的唯一規則。這些文件告訴代理接下來要做什麼、「完成」代表什麼。當文件與程式碼不一致時，以程式碼為準。

## 為什麼分成多份文件，而不是一份巨大的指令檔

一份龐雜的 `AGENTS.md` 式檔案，在規模變大後會適得其反：它佔用上下文、內容過時，還讓每件事看起來都一樣重要。依照問題而不是依照主題來切分，能讓每份文件保持簡短、讓它明顯是最新或明顯已過時，也讓每個工作階段只需載入它需要的那一份。

這種切分還帶來大型指令檔所沒有的控制特性：**bug 不能靠悄悄改寫需求來「修好」。** BRIEF.md 定義什麼必須成立；PLAN.md 定義怎麼做；LOG.md 記錄它實際上是否成立。只要三者保持分離，程式代理就無法在同一口氣裡放寬驗收標準，來掩蓋一個失敗的驗收測試——這兩個事實存放在不同的檔案裡，由不同的人負責。[CONSTITUTION.md 第二條](CONSTITUTION.md#第二條文件權限不對等)規定每份文件由誰修改。

### 讓每份文件銳利，而不是含糊

- **BRIEF.md** 只有在必要需求可以測試時才有用。「使用者可以登入」讓代理無從檢查。「輸入錯誤的憑證時回傳錯誤，且不透露該帳號是否存在」就可以。在開始實作之前，把每個必要需求都轉成驗收標準——並寫下哪些明確**不在範圍內**，因為模型會自行添油加醋，而 brief 是唯一說「不」的地方。
- **PLAN.md** 是可執行的工作佇列。一個沒有停止條件（「當這些驗收標準通過時即完成」）的任務，等於邀請代理無止境地「改進」下去。架構粗略規劃；只精確規劃接下來的幾個任務，並在目前這一段完成後再規劃下一段，而不是試圖預先預測整個專案。
- **LOG.md** 讓全新的代理工作階段讀 30 秒就能開始產出，而不必從頭重新推導狀態。保持它的營運性質：目前狀態的段落直接改寫，工作階段紀錄則往後追加。不要敘述過程。Git 已經有詳細歷史——LOG.md 承載的是 Git 無法提供的語意摘要：什麼已實際驗證、什麼正在卡關、下一步是什麼。

## 驗證

自然的工作流程是意圖 → 實作 → 記憶。這少了一步。它應該是意圖 → 實作 → 驗證 → 記憶——否則「代理說完成了」就是唯一的訊號，而這正是那個會無聲失效的訊號。

驗證存在於測試、CI 與 PLAN.md 的驗證矩陣中；LOG.md 記錄結果。一個工作階段的循環：

1. 閱讀 CONSTITUTION.md、BRIEF.md、PLAN.md、LOG.md，以及最近的 Git 狀態。
2. 在修改之前，確認應用程式目前可以運作。
3. 從 PLAN.md 的工作佇列中挑一個有界限的項目。
4. 實作它。
5. 執行確定性的關卡：建置、lint、型別、測試。
6. 直接拿結果和 BRIEF.md 的驗收標準比對——而不是和「現在應該可以了」的模糊感覺比對。
7. 檢查 diff，找出任何非預期的變更。
8. Commit。
9. 把完成的項目從 PLAN.md 的工作佇列移除，並把結果追加到 LOG.md。
10. 只有在工作樹乾淨時，才開始下一個項目。

## 完成陷阱，以及如何堵住它

打造某個功能的代理，並不是判斷該功能是否完成的可靠裁判——它就是剛剛說服自己目前實作是正確做法的同一個模型。不要問「我們都完成了嗎？」而要問：

> 假設實作尚未完成。逐條比對 BRIEF.md 中的每一項驗收標準與儲存庫，並提出它已被滿足的證據。任何沒有證據的標準都視為未完成。

在每個里程碑之後、宣告完成之前，把這件事當成獨立的一輪來執行。缺口會變成新的 PLAN.md 項目；重複，直到再也找不到缺口為止。

## 如何使用這個資料夾

1. 把 `CONSTITUTION.md`、`BRIEF.md`、`PLAN.md`、`LOG.md`，以及——在有真正的部署之後——`RUNBOOK.md` 複製到新專案的 `docs/`。
2. 在 `CONSTITUTION.md` 的第四條與第五條填入這個專案實際的不可妥協事項，其餘部分就視為完成——每個專案都使用同一套治理結構。
3. 先寫 `BRIEF.md`，附上可測試的驗收標準與明確的範圍外清單。
4. 讓 `PLAN.md` 的工作佇列一次增加一段有界限的工作，而不是一次全部列出。
5. 每個工作階段都讓 `LOG.md` 保持最新。
6. 在專案的 `AGENTS.md` 或 `CLAUDE.md` 中指向這些檔案，讓每個工作階段都先讀它們（[與程式代理協作](../03-working-with-coding-agents.md#上下文工程)）。
