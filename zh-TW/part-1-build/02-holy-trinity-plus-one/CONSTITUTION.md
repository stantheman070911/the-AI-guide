# [PROJECT_NAME] — 憲章（Constitution）

最後更新：[YYYY-MM-DD]
角色：所有其他文件與每個代理工作階段都必須遵守的永久規則

這是程式代理唯一不得自行編輯的文件。這裡的修改須經人類核准、經過深思，而且很少發生。讓這份檔案保持**簡短——50 到 150 行。** 一份沒人記得住的憲章就不會再被閱讀；地圖勝過百科全書。

## 第一條——每份文件負責什麼

| 文件 | 回答的問題 | 負責 | 不得包含 |
| --- | --- | --- | --- |
| **BRIEF.md** | 我們要做什麼、為什麼？ | 需求、使用者可見的行為、驗收標準、範圍決策 | 實作細節、狀態、歷史 |
| **PLAN.md** | 我們怎麼做？ | 架構、限制、剩餘工作的順序、驗證規則 | 已經發生之事的紀錄 |
| **LOG.md** | 現在實際上什麼是真的？ | 狀態、驗證結果、阻礙、決策、眼前目標 | 需求；未來工作該如何打造的指示 |
| **RUNBOOK.md** | 我們怎麼發布、啟用與復原？ | 維運程序 | 目前狀態——改為指向 LOG.md |
| 程式碼 + 測試 + Git | 實際上存在什麼？ | 機器事實 | — |

這四份文件**控制**工作。它們永遠不得凌駕於儲存庫、測試套件與 Git 歷史實際證明的事實之上。當文件與程式碼不一致時，在證明相反之前，程式碼是對的、文件是錯的。

**變更的歸屬：**

| 變更類型 | 處理方式 |
| --- | --- |
| 產品範圍或驗收標準 | 更新 BRIEF.md；只有在實作必須改變時才更新 PLAN.md；在 LOG.md 記下影響 |
| 架構、實作、順序 | 更新 PLAN.md；若目前狀態改變則更新 LOG.md；除非產品行為改變，否則不動 BRIEF.md |
| 維運程序 | 更新 RUNBOOK.md |
| 狀態、阻礙、完成、優先順序 | 只更新 LOG.md |
| 已解決、沒有留下持久限制的事故 | 記錄在四份文件之外，或直接刪除 |

**一個事實，一個歸宿。** 文件可以引用另一份文件負責的事實，但絕不能保留自己的副本。當兩份文件不一致時，以負責的文件為準，並修正另一份。

## 第二條——文件權限不對等

不要讓代理自由編輯全部四份文件——代理就是這樣悄悄地靠改寫需求、而不是改寫程式碼，來「解決」困難的需求。

| 文件 | 誰可以修改 |
| --- | --- |
| CONSTITUTION.md | 只有人類。代理可以提議修改；絕不能在未被要求時套用。 |
| BRIEF.md | 須經人類核准。當實作暴露出真正的產品模糊之處時，代理可以提議修訂，但不在未被要求時合併。 |
| PLAN.md | 人類與代理協作——這是實作期間的日常工作文件。 |
| LOG.md | 主要由代理維護。目前狀態的段落直接更新；工作階段紀錄只往後追加，除了更正事實錯誤之外絕不改寫。 |

## 第三條——保留原則

文件只保存仍然有用的內容。每一行都必須回答下列其中一項：產品必須做什麼；必須如何打造或驗證；現在什麼是真的；下一個維運步驟是什麼。不回答任何一項的句子，應該放在 Git 歷史、issue 追蹤系統，或哪裡都不放。

當狀態改變時，新的陳述**取代**舊的——LOG.md 不累積一本記錄過時狀態的日記。從缺陷中學到的教訓，如果違反它會重現該缺陷，就可以成為永久規則；保留規則與最少的理由，而不是事故經過。

## 第四條——工程規則

不可妥協，不論任何單一工作階段當下做了什麼決定：

- 絕不能只因為代理說任務完成就標記為完成。完成必須經過獨立驗證，確認符合 BRIEF.md 中的驗收標準。
- 每個必要需求在開始動工前，都有一個可觀察的驗收標準。
- 絕不為了讓測試套件變綠而弱化、略過或移除失敗的測試。修正根本原因。
- 沒有在 PLAN.md 寫下一行必要理由，就不新增相依套件。
- 機密絕不進入原始碼、聊天或已 commit 的檔案。
- 涉及安全或隱私的變更，在合併前要經過明確的人類審查。
- 工作以小而可獨立驗證的增量合併——而不是一次巨大、無法審查的變更。

## 第五條——兩種風險模式

同一個代理，不同的風險預算。本條定義兩種模式；LOG.md 記錄每個面向目前處於哪種模式：

| 模式 | 適用時機 | 有何不同 |
| --- | --- | --- |
| **Vibe 模式** | 本機原型、沒有真實使用者、沒有真實資料、沒有損失風險 | 自由度高、快速迭代、流程輕量 |
| **工程模式** | 真實使用者、真實資料、金流、憑證，或正式環境部署 | 驗收標準、測試、安全審查、完整 diff 審查與受控部署都成為必要 |

對某個面向而言，從 vibe 模式轉到工程模式是一扇單向門——不要在真實使用者依賴的程式碼上，悄悄退回 vibe 模式的自由度。
