# 附錄 E：程式碼庫稽核提示詞

一份只做審查、不做修改的提示詞，用來稽核已完成的程式碼庫。它要求 AI 程式代理找出最少、但能實質改善專案的修改，而不是列出最多的問題。

## 使用方式

1. 在程式代理中開啟專案，把下方區塊貼上作為任務。
2. 代理不應修改任何東西。如果你的工具有唯讀模式或規劃模式，請使用它。
3. 採取行動前，先對照程式碼檢查每一項發現。發現是待驗證的主張，不是已確認的修正。
4. 依建議的優先順序一次處理一項。每項修改的做法請見[附錄 B](02-claude-md-coding-rules.md)。

## 提示詞

```markdown
# 程式碼庫稽核與審查

這是一個已完整實作的專案。請稽核現有程式碼庫，只找出真正值得進行的改善。

指導原則：
「沒有什麼比高效率地去做根本不該做的事更無用。」

## 1. 做法

* 先理解，再評估。下結論之前，先探索專案架構、關鍵模組、資料流、相依套件、慣例與限制。
* 聚焦於重要的事。評估安全性、正確性、可靠性、效能與可維護性。其他面向只有在影響重大時才納入。
* 先驗證，再回報。指出問題之前，先追蹤相關的程式路徑並檢查既有的防護措施。區分已確認的問題與潛在風險。
* 只做審查。不要修改程式碼、設定、相依套件或任何專案檔案。

## 2. 審查標準

* 價值重於數量。只有在修正能帶來明確、實際的好處時才回報問題。不要為了填滿分類而製造發現。
* 證據重於推測。每項發現都要以實際實作為根據，並附上檔案路徑與行號。明確說明任何不確定性或驗證上的限制。
* 簡單重於複雜。優先移除、合併或簡化程式碼，而不是引入新機制。只有在效益明顯大於成本時，才建議新增相依套件、抽象層或架構層。
* 影響重於慣例。忽略外觀問題、主觀的風格偏好、泛泛的最佳實踐，以及沒有可信失敗情境的假設性風險。
* 移除不必要的工作。當移除能實質改善專案時，指出死碼、重複邏輯、不必要的複雜度與過度設計。
* 尊重既有決策。考量專案實際的需求、規模、架構與慣例。不要只因為偏好另一種設計哲學就建議修改。
* 避免重複的發現。把根本原因相同、或可以用同一項修改解決的問題合併。

## 3. 輸出

### 架構概覽

簡要說明架構、關鍵模組、主要資料流、重要模式、相依套件與相關限制。只納入理解發現所需的脈絡。

### 發現

依嚴重程度分組：

* Critical（嚴重）：立即的安全性、資料完整性或系統可用性風險。
* High（高）：重大的正確性、安全性、可靠性或效能問題，且有可信的實際影響。
* Medium（中）：值得修正但不緊急的實質弱點或不必要的複雜度。
* Low（低）：方便時值得進行的小幅、可證明的改善。

每項發現請提供：

* 位置：檔案路徑與行號。
* 問題：哪裡出錯、為什麼。
* 影響：具體後果，包括發生的條件。
* 最小修正：最簡單有效的修正方式。
* 工作量：小（S）、中（M）或大（L）。

依嚴重程度與實際影響排序。省略沒有內容的分類。

### 建議優先順序

列出最多 5 項最值得先處理的改善，依影響、急迫性、工作量與風險降低程度排序。

簡要說明每一項為何值得優先處理。如果值得處理的改善少於 5 項，就列出較少的項目。

## 4. 最終限制

* 不要做任何修改。
* 不要把未驗證的假設當成已確認的發現。
* 當針對性的修正就足夠時，不要建議大範圍重構。
* 沒有可證明的淨效益時，不要引入複雜度。
* 不要把發現的數量當成稽核的品質。

目標不是找出最多的問題，而是找出能實質改善程式碼庫的最少修改。
```
