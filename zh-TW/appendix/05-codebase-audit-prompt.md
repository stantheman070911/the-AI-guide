# 附錄 E：程式碼庫稽核提示詞

一份只做審查、不做修改的提示詞，用來稽核已完成的程式碼庫。它要求 AI 程式代理找出最少、但能實質改善專案的修改，而不是列出最多的問題。

## 使用方式

1. 在程式代理中開啟專案，把下方區塊貼上作為任務。
2. 代理不應修改任何東西。如果你的工具有唯讀模式或規劃模式，請使用它。
3. 採取行動前，先對照程式碼檢查每一項發現。發現是待驗證的主張，不是已確認的修正。
4. 依建議的優先順序一次處理一項。每項修改的做法請見[附錄 B](02-claude-md-coding-rules.md)。

## 提示詞

```markdown
# 程式碼庫稽核與審查

## 目標

這是一個既有、已完整實作的專案。請稽核程式碼庫，只找出能實質改善其安全性、正確性、可靠性、效能或可維護性的改善。

目標不是盡量增加發現、強推理想化的架構，或製造不必要的工作，而是找出能帶來實質、可證明價值的最少修改。

指導原則：
「沒有什麼比高效率地去做根本不該做的事更無用。」

## 1. 稽核做法

### 先理解，再評估

下結論之前，先建立足夠的脈絡。

* 檢視架構、關鍵模組、進入點、相依套件、設定與主要資料流。
* 確認專案的預期行為、執行環境、規模與相關限制。
* 理解既有的慣例、防護措施、測試與架構決策。
* 追蹤跨模組的重要互動，而不是單獨評判孤立的程式片段。
* 不要因為某個模式不熟悉，就假定它錯誤或多餘。

### 依風險與影響調查

優先調查缺陷或複雜度會造成實質後果的區域。

考量：

* 安全性：驗證、授權、輸入處理、敏感資料、信任邊界，以及可信的攻擊路徑。
* 正確性：商業邏輯、狀態轉換、邊界情況、資料完整性與錯誤處理。
* 可靠性：故障復原、資源管理、並行、交易一致性與營運韌性。
* 效能：可證明的瓶頸、低效率的操作、不必要的資源消耗與擴展限制。
* 可維護性：不必要的複雜度、重複、死碼、脆弱的耦合，以及可避免的維護成本。

依專案實際的架構與風險輪廓分配調查重點。不要強求每個面向都同等涵蓋，也不要為每個分類硬找發現。

### 先驗證，再回報

對每個潛在問題：

1. 找出負責的確切實作。
2. 追蹤相關的執行路徑，以及受影響的呼叫端或使用端。
3. 檢查既有的驗證、防護措施、限制或測試是否已處理這個疑慮。
4. 確立問題發生所需的條件。
5. 在專案的預期用途下，評估實際的影響與發生可能性。
6. 判斷修正帶來的好處相對於其成本與複雜度是否有實質意義。

區分以下三種：

* 已確認：實作提供了足夠證據，證明問題存在。
* 可信但未驗證：存在實際的風險，但某個特定假設或執行時條件尚未驗證。
* 推測：疑慮缺乏足夠證據或可信的失敗情境。

只回報已確認的問題，以及實質、可信的風險。清楚標示任何未解決的假設。省略推測性的疑慮。

不要把缺少測試、理論上的邊界情況或可能的未來需求，等同於已確認的缺陷。

### 唯讀執行

這純粹是稽核。

* 不要修改原始碼、設定、相依套件、測試或專案檔案。
* 不要安裝套件、套用修正、產生檔案，或執行會改變專案或外部狀態的指令。
* 使用唯讀的檢視與安全的驗證方法。
* 如果驗證需要被禁止的動作，記錄這項限制，而不要執行它。

## 2. 審查標準

### 價值重於數量

每項發現都必須值得為它投入修正的工作。

不要為了填滿分類或達到隱含的發現數量而製造問題。沒有可行動發現的稽核，也是有效的結果。

### 證據重於推測

結論要以實際實作為根據。

提供精確的檔案路徑與行號。說明相關的執行路徑、既有的防護措施與失敗條件。

絕不要把假設、推論出的行為或未執行的測試當成已驗證的事實。

### 簡單重於複雜

優先採用最小而有效的修正。

適當時，優先移除、合併或簡化既有程式碼。只有在效益明顯大於成本時，才建議新增抽象層、相依套件、基礎設施或架構層。

不要只因為另一種做法更流行或理論上更易擴充，就建議取代一個可運作的設計。

### 影響重於慣例

忽略：

* 外觀問題與主觀的風格偏好。
* 沒有專案特定理由的泛泛最佳實踐建議。
* 沒有可信攻擊或失敗路徑的理論性漏洞。
* 對效能沒有實質影響的過早最佳化。
* 沒有已證明重複或脆弱性的缺少抽象。
* 沒有相關實質風險的缺少測試。
* 推測性的需求或假設性的未來規模。

### 移除不必要的工作

當移除能實質降低複雜度、風險或維護工作時，主動找出死碼、多餘的操作、重複邏輯、不必要的相依套件與過度設計。

不要建議成本超過實際效益的清理。

### 尊重既有決策

依專案實際的需求、限制、慣例與預期的執行條件來評估專案。

除非能證明既有做法造成實質問題，否則不要強加另一種架構哲學。

### 合併根本原因

避免重複或重疊的發現。

當多個症狀來自同一個根本原因時，回報一項發現，涵蓋底層問題及其重要後果。

## 3. 回報門檻

納入一項發現之前，先回答以下問題：

1. 證據：哪段具體的程式碼證明了問題？
2. 情境：在什麼實際條件下它才重要？
3. 影響：會造成什麼具體的失敗、風險、浪費或維護負擔？
4. 既有防護：這個疑慮是否已在別處被預防或緩解？
5. 補救：最簡單有效的修正是什麼？
6. 價值：預期效益是否值得實作與維護的成本？

如果無法充分回答這些問題，就進一步調查，或省略這項發現。

不要只因為發現的問題很少，就降低回報門檻。

## 4. 輸出格式

### 架構概覽

簡要說明：

* 整體架構與關鍵模組。
* 主要執行路徑與資料流。
* 重要的相依套件與設計模式。
* 相關限制與既有的防護措施。

只納入理解稽核發現所需的脈絡。

### 發現

依嚴重程度分組。

* Critical（嚴重）：對安全性、資料完整性或系統可用性的立即或容易被利用的風險。
* High（高）：重大的正確性、安全性、可靠性或效能問題，且有可信的實際影響。
* Medium（中）：值得修正但不緊急的實質弱點、營運風險或不必要的複雜度。
* Low（低）：方便時值得處理的小幅、可證明有益的改善。

每項發現請提供：

* 標題：簡潔描述底層問題。
* 嚴重程度：Critical／High／Medium／Low。
* 位置：確切的檔案路徑與行號，必要時包括相關位置。
* 證據：支持結論的相關實作細節與執行路徑。
* 問題：哪裡出錯，以及既有行為為何不足。
* 影響：具體後果，以及發生的條件。
* 驗證：已確認或可信但未驗證，包括任何假設或限制。
* 最小修正：處理根本原因的最簡單修正。
* 工作量：小（S）、中（M）或大（L）。

依嚴重程度與實際影響排序。在同一嚴重程度內，考量發生可能性與影響範圍來排序。

省略沒有內容的嚴重程度分類。

不要捏造檔案路徑、行號、執行行為、測試結果或佐證。

### 建議優先順序

列出最多五項最值得先實作的改善。

依以下標準排序：

1. 預期影響與風險降低程度。
2. 嚴重程度與急迫性。
3. 對該發現的信心。
4. 實作工作量與複雜度。
5. 可能的回歸風險。

簡要說明每項改善為何值得優先處理，並註明對應的發現。

不要自動把大型架構修改排在能帶來相當效益的較小修正之前。

如果值得處理的改善少於五項，就建議較少的項目。

### 涵蓋範圍與限制

簡要指出：

* 檢視過的主要區域。
* 未充分檢視的重要區域。
* 實質影響結論可信度的驗證限制。

如果稽核是選擇性的或受到限制，不要暗示涵蓋了全部。

如果沒有任何發現達到回報門檻，明確說明這一點，不要捏造建議。

## 5. 最終限制

* 不要做任何修改。
* 不要把假設當成已確認的缺陷回報。
* 不要把不熟悉的程式碼當成錯誤的程式碼。
* 當針對性的修正就足夠時，不要建議大範圍重構。
* 沒有可證明的淨效益時，不要引入複雜度。
* 不要讓假設性的未來準備凌駕於當前需求之上。
* 不要重複回報根本原因相同的發現。
* 不要把稽核的篇幅或發現的數量當成稽核的品質。
* 不要建議預期效益不足以抵銷成本的工作。

最終目標：產出一份以證據為本、排定優先順序的評估，只找出真正值得進行的修改。每項建議都應站得住腳、合乎比例且可行動。一份乾淨的稽核，勝過一串製造出來的問題。
```
