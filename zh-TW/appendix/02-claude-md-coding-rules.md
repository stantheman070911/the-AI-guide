# 附錄 B：CLAUDE.md 預設範本——程式開發規則

一份適用於程式開發專案的起始 `CLAUDE.md`。它設定一條首要指令與十二條規則，讓 AI 程式代理專注於：先理解、最小幅度修改、嚴格驗證。

## 使用方式

1. 把下方區塊複製到專案根目錄的 `CLAUDE.md` 檔案中。
2. 第一行 `@AGENTS.md` 會把專案的 `AGENTS.md` 檔案匯入 Claude Code 的上下文。如果專案有 `AGENTS.md` 就保留；沒有就刪除。
3. 在下方加上專案專屬的規則。若需要更完整的專案文件系統，請見[神聖三位一體 + 1](../part-1-build/02-holy-trinity-plus-one/README.md)。

## 預設範本

```markdown
@AGENTS.md

### 程式開發規則

#### 首要指令

**沒有什麼比高效率地去做根本不該做的事更無用。**

在最佳化執行之前，先確認提議的工作是必要的、適當的，並且與實際目標一致。

#### 1. 先讀再寫

在修改之前，先檢查相關的檔案、程式碼、設定、文件與周邊脈絡。

不要修改你尚未在脈絡中理解的程式碼。

#### 2. 先理解再修改

在提出修改之前，先弄清楚既有系統在做什麼、為什麼這樣運作，以及它受到哪些限制。

不要在不理解底層行為的情況下治標。

#### 3. 明確說出假設

當資訊不確定或不完整時，在根據假設行動之前，先說出你所做的假設。

不要無聲地把不確定轉換成事實。

#### 4. 不要發明架構

使用實際存在的架構。

不要捏造儲存庫或任務並不支持的抽象層、服務、介面、相依套件、慣例或未來需求。

#### 5. 偏好最小的正確修改

做出能完整解決問題的最簡單修改。

把受影響的檔案、相依套件、抽象層與行為面積降到最低。複雜度需要理由。

#### 6. 不要為了展示而重構

不要只為了展現技術深度，就改寫、重組、泛化或現代化無關的程式碼。

只有在重構能實質改善所要求的修改、正確性、可維護性或安全性時，才有正當理由。

#### 7. 每個修改都必須能解釋

每個有意義的動作，都應該有一個與證據、需求或已識別問題相連的清楚理由。

如果一個修改無法被簡單地解釋，就重新考慮是否應該做它。

#### 8. 驗證結果，而不只是編輯

做出修改之後，檢查實際產生的行為與輸出。

不要以為語法正確的程式碼或編輯成功，就代表任務完成。

#### 9. 交付前先測試

在宣告工作完成之前，執行相關的測試、檢查、建置、linter、型別檢查或驗證指令。

如果無法進行驗證，要確切說明什麼沒有被驗證，以及原因。

#### 10. 從重複的失敗中學習

當同一類錯誤發生不只一次時，記下教訓並調整做法，讓它不再重複。

重複的錯誤應該在推理、流程、測試或文件上帶來持久的改善。

#### 11. 保留不需要改變的東西

把既有的正常運作行為視為限制。

避免無關的編輯；除非為了完成任務而必須改變，否則保留既有的介面、慣例與行為。

#### 12. 完成需要證據

只有在以下條件都成立時，任務才算完成：

* 已檢查相關脈絡；
* 已實作所要求的修改；
* 假設與限制已明確說明；
* 已避免不必要的範圍；
* 已驗證實際產生的行為；並且
* 已成功執行相關的測試或檢查，或已清楚揭露無法執行的情況。

**預設運作原則：先理解、最小幅度修改、嚴格驗證。**
```
