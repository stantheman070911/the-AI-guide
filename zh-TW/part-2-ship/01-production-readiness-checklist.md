# 網站上線準備檢查清單

一份整合過的檢查清單，用於把「vibecoded」網站——快速建成、往往大量依賴 AI 協助的網站——推上正式環境。重疊的項目（favicon、404 處理、標題、meta description、`robots.txt`、替代文字、行動裝置溢出等）已經合併，每一點只出現一次。

## 1. 網域、品牌與基本上線打磨

* 連接自訂網域，而不是只使用 `*.vercel.app`
* 加上 favicon
* 替換預設的「Vite」、「React」、「Next.js」瀏覽器標題
* 讓每個重要頁面都有獨一無二的頁面標題
* 加上真正的 logo，並讓它可以點擊回到首頁
* 修正版權年份
* 移除佔位文字與未使用的導覽項目
* 在適當的地方，用真實的公司／團隊照片取代通用圖庫圖片

## 2. 行動裝置與響應式設計

* 讓每個頁面都針對行動裝置最佳化；移除水平捲動並修正溢出
* 加上適當的行動版導覽選單
* 在小螢幕尺寸下檢查點擊區域、字體排印與圖片是否被正確容納
* 在行動裝置上檢查表格、卡片與表單
* 在適當的地方加上固定在畫面上的行動版 CTA
* 測試常見寬度：320px、375px、390px、430px、平板與桌機

如果桌機版正常、行動版只是「縮小」，這個網站就還沒準備好上線。

## 3. 導覽與失效的互動

* 找出並修復失效的連結、按鈕與頁尾連結
* 讓電話號碼可以用 `tel:` 點擊、電子郵件地址可以用 `mailto:` 點擊
* 檢查所有導覽連結、CTA 目的地、外部連結與錨點連結
* 移除失效的導覽項目
* 確認瀏覽器的上一頁／下一頁正常運作

## 4. 錯誤處理與使用者回饋

* 加上自訂、有用的 404 頁面——不只是裝飾
* 在表單／操作之後加上成功與錯誤訊息，以及看得見的載入狀態
* 避免按鈕在請求期間看起來毫無反應
* 妥善處理失敗的 API 請求、空狀態，以及過期／無效的網址
* 從使用者看得到的介面中移除原始的框架／伺服器錯誤

## 5. 表單與潛在客戶開發

* 在首屏加上清楚、明顯的行動呼籲（CTA）
* 在表單送出後加上感謝頁面與確認／成功狀態
* 加上有用的驗證訊息；避免要求不必要的資訊
* 端對端測試所有聯絡表單，確認詢問確實送達目的地
* 在商業上適當時加上回覆時間承諾（例如「我們通常在一個工作天內回覆」——這能降低不確定感，並可能實質提升轉換率）
* 把表單送出追蹤為轉換

## 6. SEO 基礎

* 每個重要頁面都有獨一無二的 `<title>` 與 meta description
* 加上 canonical 標籤、`robots.txt` 與 `sitemap.xml`
* 確保重要頁面可以被索引；確認沒有意外啟用 `noindex`
* 在適當的地方加上內部連結與麵包屑；使用具描述性的網址
* 避免重複的頁面／內容
* 一致地把 HTTP 重新導向到 HTTPS，並統一重複的主機名稱版本
* 網址變更時設定正確的 301 重新導向

## 7. HTML 結構與語意 SEO

* 每個重要頁面只有一個有意義的 `<h1>`——避免互相競爭的 `<h1>` 標題
* 使用合乎邏輯的 `h1 → h2 → h3` 層級
* 為 `<html>` 加上 `lang` 屬性
* 使用語意元素（`header`、`nav`、`main`、`section`、`article`、`footer`），而不是全部用通用的 `<div>` 堆出來

目標是一個連貫的文件層級，而不只是滿足 SEO 檢查工具。

## 8. 圖片 SEO 與無障礙

* 為有意義的圖片加上有用的替代文字；裝飾性圖片使用空的替代文字
* 避免在替代文字中堆砌關鍵字
* 壓縮圖片、提供適當尺寸的版本，並優先使用新式格式
* 延遲載入首屏以下的圖片
* 設定圖片的寬度／高度以減少版面位移

## 9. 社群分享

* 加上 Open Graph 中繼資料：標題、描述、canonical／分享網址，以及分享圖片
* 在相關時加上 Twitter/X card 中繼資料
* 實際測試連結被分享時看起來如何

你不會希望有人分享你的商家時，出現「Vite \+ React」、像 localhost 一樣的標題、沒有圖片，以及一段莫名其妙的描述。

## 10. 結構化資料／Schema

* 加上相關的 Schema.org 結構化資料（LocalBusiness、Organization、Breadcrumb、FAQ，前提是適用且與可見內容一致）
* 正確加入聯絡／商家資訊，並驗證結構化資料
* 讓 schema 與使用者實際看得到的內容保持一致

## 11. 在地商家網站

適用於水電工、承包商、牙醫、餐廳、代理商、診所等：

* 加上商家地址、可點擊的電話號碼、營業時間、地圖與路線指引
* 加上 LocalBusiness schema 與服務區域資訊
* 加上真實的顧客評論、推薦見證，以及專案／顧客照片
* 在真正有用的地方加上地點／服務頁面
* 讓 NAP 資訊（名稱 Name、地址 Address、電話 Phone）在每個出現的地方都保持一致

## 12. 信任與轉換

* 在首屏放上清楚的 CTA 與價值主張；說明產品／服務是給誰的
* 加上附出處的真實顧客評論與推薦見證，以及案例研究區塊
* 加上大約五個有用的常見問題，以及回覆時間的預期
* 加上真實的團隊／公司照片與聯絡資訊
* 在適當時加上隱私權政策與服務條款
* 只有在真實時才加上信任標誌——避免捏造的 logo、評論或推薦見證

## 13. 內容品質

* 移除 AI 佔位文案、「Lorem ipsum」，以及「我們提供創新的解決方案」這類空泛的宣稱
* 移除重複的區塊；檢查拼字與文法；查證所有事實陳述
* 讓 CTA 具體，並清楚說明服務／產品
* 讓首頁訊息在幾秒內就能被理解
* 確保每個頁面都有清楚的目的

常見的 vibecoding 失敗，是一個技術上能運作、但文案幾乎什麼都沒說的網站。

## 14. 可爬取性與渲染

* 檢查「檢視原始碼」裡出現什麼，並確認爬蟲能取得關鍵內容
* 避免不必要地把整個網站都做成用戶端渲染
* 確認頁面中繼資料在適當時是由伺服器端渲染
* 如果 SEO 很重要，檢查停用或降級 JavaScript 時的頁面
* 檢查 robots 指令，並刻意決定要允許還是封鎖 AI 爬蟲

「檢視原始碼」看起來是空的，是一個警訊，但不一定是 bug。對應用程式或儀表板來說，大量用戶端渲染可能是合理的；對 SEO 登陸頁來說，就值得調查。

## 15. 數據分析與成效衡量

* 安裝數據分析工具（Google Analytics、PostHog，或其他刻意選擇的組合），並確認它在正式環境中確實觸發
* 追蹤主要 CTA 點擊、表單送出與轉換（註冊、購買／訂閱完成等）
* 在有用時排除內部／測試流量
* 避免蒐集不必要的個人資訊

## 16. 效能

* 壓縮圖片；移除巨大的 JS bundle 與未使用的相依套件
* 對昂貴的元件做程式碼分割與延遲載入；避免把伺服器端函式庫送到用戶端
* 稽核第三方腳本，並最佳化字型
* 避免版面位移；檢查 Largest Contentful Paint、Interaction to Next Paint 與 Cumulative Layout Shift
* 在較慢的行動網路與較低階的硬體上測試

Vibecoded 網站常常在開發者的 MacBook 上表現良好，卻在真正顧客的手機上表現很差。

## 17. 瀏覽器主控台與正式環境衛生

* 正式環境的主控台不應該滿是錯誤——修正失敗的網路請求、框架警告與 hydration 錯誤
* 移除除錯日誌、開發用橫幅，以及未使用的程式碼／資源
* 停用除錯模式，並檢查正式環境的設定
* 刻意決定是否要公開正式環境的 source map
* 驗證正式環境的建置結果，而不是只依賴本機開發模式

## 18. 機密與 API 金鑰

**這是關鍵，不是選配的打磨。**

* 隱藏 API 金鑰；絕不把機密金鑰放進前端 JavaScript
* 稽核環境變數，區分公開與私密的變數
* 檢查 Git 歷史（包括舊的分支／標籤）中是否意外 commit 了機密，並輪替任何已外洩的東西
* 在供應商支援時限制 API 金鑰；開發與正式環境使用不同的憑證
* 確保 `.env` 檔案沒有被 commit，並確認建置日誌不會洩漏機密

最高風險的 vibecoding 錯誤之一，就是請 AI 串接某個 API，結果不小心把機密一起打包進用戶端 bundle 送出去。

*關於寫死在程式碼中的憑證與外洩的用戶端金鑰，詳細的修補步驟請見[資安修補手冊](02-security-remediation-playbook.md#機密與金鑰)。*

## 19. 身分驗證與授權

* 有私密功能時就加上身分驗證；保護管理員路由與 API
* 在伺服器端驗證身分並檢查權限
* 把授權與身分驗證分開實作；防止使用者請求其他使用者的資料
* 手動測試未經驗證的請求，以及低權限使用者嘗試執行管理員操作

**關鍵原則**：對使用者隱藏的按鈕，不等於拒絕存取。授權必須由伺服器／資料庫強制執行。

*關於用戶端身分驗證、IDOR、失效的存取控制、session 處理與身分驗證繞過路徑，詳細的修補步驟請見[資安修補手冊](02-security-remediation-playbook.md#身分驗證與授權)。*

## 20. 資料庫安全

* 檢查資料庫存取規則；在適用時啟用 Row Level Security
* 測試資料庫政策，並防止未經授權的直接寫入
* 將資料庫查詢參數化，並採用最小權限存取
* 絕不把服務／管理員資料庫憑證暴露給瀏覽器
* 備份重要資料，並確認破壞性操作需要適當的授權

特別是 Supabase，一個非常常見的 vibecoding 錯誤是先做 UI、之後才發現權限問題，然後讓資料表維持過度寬鬆，好讓應用程式「能動」。

## 21. 輸入與應用程式安全

* 清理並驗證使用者輸入——在伺服器端，而不只是在用戶端
* 防範 XSS、SQL 注入 與不安全的網址重新導向
* 驗證 ID 與物件擁有權；拒絕非預期的輸入並限制 payload 大小
* 避免盲目渲染 AI 或使用者產生的 HTML；適當地跳脫輸出

*關於 SQL 注入、XSS 與命令注入，詳細的修補步驟請見[資安修補手冊](02-security-remediation-playbook.md#注入漏洞)。*

## 22. 濫用防範與成本保護

對 AI 產品尤其重要。

* 加上速率限制，特別是身分驗證端點、昂貴的 API 與 AI 生成端點
* 保護聯絡表單免受垃圾訊息，並加上合理的請求大小限制
* 在支援時加上供應商的帳單／支出警示與支出上限
* 在適當時加上每位使用者的用量配額，防止無限制地執行昂貴工作

一個沒有速率限制的 AI 端點，可能很快就把每月 20 美元的基礎設施帳單，變成 2,000 美元的意外帳單。

*詳細的修補計畫請見[資安修補手冊第 16 項](02-security-remediation-playbook.md#16-缺少速率限制---高)。*

## 23. 檔案上傳安全

* 在適當時要求身分驗證；限制檔案類型並驗證 MIME 類型
* 限制檔案大小上限，並在伺服器端產生檔名，而不是信任使用者提供的檔名
* 在不適當的情況下防止上傳可執行檔；限制儲存空間的權限
* 防止使用者存取屬於他人的私密上傳檔案；避免意外公開私密的儲存 bucket
* 對較高風險的系統，考慮惡意軟體掃描

## 24. 網站安全設定

* 啟用 HTTPS，並把 HTTP 重新導向到 HTTPS
* 加上適當的安全標頭：CSP、HSTS、MIME 嗅探與框架嵌入防護
* 用 `HttpOnly`、`Secure` 與適當的 `SameSite` 政策保護 cookie
* 檢查 CORS 設定；敏感的 API 避免使用 `Access-Control-Allow-Origin: *`
* 在身分驗證架構需要時加上 CSRF 防護

*關於安全標頭與 CSRF，詳細的修補步驟請見[資安修補手冊](02-security-remediation-playbook.md#安全標頭與防護)。*

## 25. 部署與正式環境設定

* 檢查所有正式環境變數，以及預備環境（staging）與正式環境的設定差異
* 停用除錯模式與僅供開發使用的端點
* 檢查正式環境的 API 網址、OAuth 重新導向網址、webhook 網址與允許的來源
* 確認電子郵件使用正式網域，且金流系統處於正確的模式
* 確認資料庫指向正式環境，且備份、監控與錯誤追蹤都已就位
* 從乾淨的建置測試部署

## 更高層次的稽核

上面的檢查清單可以歸納為八道上線關卡：

| 關卡 | 問題 |
| ----- | ----- |
| 1\. 它能運作嗎？ | 連結、按鈕、表單、路由、404、錯誤 |
| 2\. 它在行動裝置上能運作嗎？ | 響應式設計、溢出、選單、點擊區域 |
| 3\. 人們找得到它嗎？ | SEO、中繼資料、sitemap、robots、schema |
| 4\. 它能轉換嗎？ | CTA、評論、常見問題、案例研究、表單 |
| 5\. 它看起來正當可信嗎？ | 網域、favicon、品牌、真實的內容／照片 |
| 6\. 它夠快嗎？ | 圖片、JS bundle、渲染、Core Web Vitals |
| 7\. 我們能衡量它嗎？ | 數據分析、轉換、錯誤監控 |
| 8\. 它會被攻擊嗎？ | 機密、身分驗證、授權、輸入、資料庫、上傳、濫用 |

在 AI／vibecoding 時代，最後一道關卡最值得重視：糟糕的中繼資料讓網站看起來很業餘，但糟糕的授權可能讓整個客戶資料庫外洩。

把檢查清單分成三個嚴重等級看待：

* **P0——安全／資料／金錢**：外洩的 API 金鑰、身分驗證、權限、資料庫規則、上傳、速率限制、金流設定、正式環境設定。
* **P1——功能／轉換**：失效的連結、表單、按鈕、行動裝置、錯誤、CTA、404。
* **P2——可發現性／打磨**：SEO、schema、favicon、OG 圖片、標題、中繼資料、案例研究、常見問題。

P0 項目對應[資安修補手冊](02-security-remediation-playbook.md)中的 🚨 嚴重／🔴 高 項目。
